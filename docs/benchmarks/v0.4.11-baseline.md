## Correction to the earlier ~370 MiB estimate

The earlier architecture-design estimate of roughly 370 MiB total / 215 MiB Frameworks / 156 MiB Resources came from the repository-local `release/mac-arm64/WebGPT Bridge.app` directory. During Task 1 it was read-only checked and found to have `CFBundleShortVersionString = 0.4.5`, so it is a stale arm64 build and is **not** a valid v0.4.11 package baseline.

That stale directory remains untouched, but its measurements must not be used to claim v0.4.11 slimming progress. The verified installed v0.4.11 Universal snapshot above is the package baseline for this task.

## Reproducible logical-byte reporter

Task 1 adds:

```text
npm run size:report -- /absolute/path/to/WebGPT\ Bridge.app
```

The command prints deterministic JSON with these fields:

```json
{
  "totalBytes": 0,
  "frameworksBytes": 0,
  "resourcesBytes": 0,
  "appAsarBytes": 0,
  "appAsarUnpackedBytes": 0,
  "tunnelClientBytes": 0
}
```

The reporter recursively sums logical file sizes, sorts traversal order, treats missing components as zero, and refuses to follow symbolic links. It does not shell out to platform-specific utilities such as `du`, so the same code can be used by macOS and Windows packaging work.

The reporter's deterministic fixture baseline is:

```text
totalBytes             48
frameworksBytes        11
resourcesBytes         37
appAsarBytes            7
appAsarUnpackedBytes   13
tunnelClientBytes      17
```

The installed v0.4.11 app is outside the project sandbox, so the sandboxed Node reporter is not used to claim logical-byte values for that installed tree in this baseline. The installed package uses the separately labelled read-only Host `du`/`stat` measurements above. Future build artifacts available inside the build workspace should be measured directly with `size:report`, and comparisons should use the same reporter and artifact class on both sides.

## Comparison rules for later slimming work

1. Compare like with like: Universal to Universal, arm64 to arm64, x64 to x64.
2. Use reporter logical bytes for reproducible component deltas; use allocated `du` size only when explicitly labelled as such.
3. Never count a capability/security/runtime removal as a successful size optimization.
4. A size change is not accepted merely because the final installer is smaller; identify which component changed.
5. Formal release digests and published asset sizes continue to come from the release verification pipeline, not this benchmark document.

# WebGPT Bridge Desktop Auto-Update, Release, and Signing Design

Date: 2026-08-26
Status: Design approved; written specification pending user review

## Summary

WebGPT Bridge will add a complete in-app update flow for Windows and macOS while continuing to use public GitHub Releases as the only public distribution and update source.

The system uses `electron-updater` in the Electron main process, signed release artifacts, a draft-first GitHub Release workflow, and platform-native installation behavior:

- Windows: signed x64 per-machine NSIS update, UAC when elevation is required, then relaunch;
- macOS: Developer ID signed and notarized Universal application update, then relaunch;
- both platforms: explicit user-controlled download and installation, bounded renderer IPC, fail-closed verification, stable-only update channel, and no client-side GitHub credentials.

The release pipeline also addresses browser and operating-system trust warnings as far as direct GitHub distribution can. Windows artifacts must use one stable verified publisher identity so publisher reputation can accumulate across releases. This design does not claim that a newly established publisher will have zero SmartScreen warnings on its first downloads. macOS artifacts must be Developer ID signed and notarized so Gatekeeper can verify their origin and notarization status.

## Goals

1. Add an in-app update flow on Windows and macOS:
   - check for updates;
   - show current and available versions;
   - show bounded plain-text release notes;
   - download only after explicit user action;
   - show download progress;
   - install only after explicit `Update and restart` action;
   - restart into the newly installed version.
2. Use GitHub Releases as the sole public update feed.
3. Keep update authority in the Electron main process, not the renderer.
4. Keep GitHub tokens, Azure signing credentials, Apple signing credentials, certificate private keys, and arbitrary update URLs out of the packaged application.
5. Sign every formal Windows release with one stable public publisher identity and timestamp the signatures.
6. Sign and notarize every formal macOS release with one Apple Developer identity.
7. Produce a real Universal macOS application containing both `arm64` and `x86_64` slices.
8. Preserve the Windows AppContainer host-preparation security boundary during upgrades. The updater itself must never mutate `NUL` security, create the privileged scheduled task, or invoke the host-prep helper in mutation mode.
9. Prevent incomplete releases from becoming visible to existing clients.
10. Fail closed if update metadata, checksums, signatures, publisher identity, notarization, packaging, platform acceptance, or release-asset validation fails.

## Non-goals

The first implementation will not:

- create a Microsoft Store distribution;
- promise zero SmartScreen warnings for a new Windows publisher;
- bypass Windows UAC for the per-machine NSIS upgrade;
- silently install an update merely because the user exits the application;
- automatically download updates;
- automatically downgrade an installed version;
- expose beta/prerelease versions to stable users;
- expose an arbitrary update feed, mirror, repository, installer path, or command to the renderer;
- implement percentage staged rollout in the initial version;
- replace or weaken the current AppContainer / null-device host-preparation model;
- store formal signing credentials in the repository;
- publish unsigned formal release artifacts.

## Existing state

The root desktop package is version `0.3.4` and is built with Electron and Electron Builder.

There is currently no update subsystem:

- no `electron-updater` dependency;
- no Electron updater service;
- no update IPC;
- no update UI;
- no GitHub Release update metadata publication;
- Windows and macOS dist scripts use `--publish never`;
- Windows code signing is not configured;
- macOS Developer ID signing and notarization are not configured;
- the workflow job is named `macOS universal`, but the current `dist:mac` script builds only `--arm64`.

The existing Electron privilege boundary is suitable for the new feature: host behavior lives in the main process, renderer capabilities are exposed through preload, and renderer pages do not receive arbitrary host execution primitives.

## Architecture

### Components

The subsystem is divided into five independently testable components.

#### 1. Desktop updater service

A new focused main-process module owns `electron-updater` and all update state.

Responsibilities:

- initialize the GitHub provider configuration generated by Electron Builder;
- disable automatic download;
- disable install-on-normal-quit behavior;
- allow only stable releases;
- prohibit downgrade;
- schedule startup and periodic checks;
- deduplicate concurrent checks/downloads;
- normalize updater events into one bounded state object;
- normalize release notes to plain text;
- map errors into bounded error codes;
- coordinate orderly Bridge shutdown before explicit installation;
- invoke the platform updater only after the user chooses `Update and restart`.

For the modern updater API, installation policy is explicitly `manual` rather than the default on-quit behavior. The application must not silently install a downloaded update when the user simply quits.

#### 2. Preload update bridge

The preload bridge exposes only narrow operations:

- `getUpdateState()`;
- `checkForUpdates()`;
- `downloadUpdate()`;
- `installUpdateAndRestart()`;
- `onUpdateState(callback)`.

The renderer cannot pass an update URL, GitHub repository, target version, installer path, release channel, publisher name, file path, shell string, or installer arguments.

#### 3. Renderer update panel

The main window gains an `Application update` card between the runtime status section and advanced settings.

The card shows:

- current application version;
- check status;
- available version when newer;
- release date when available;
- bounded plain-text release notes;
- download percentage, byte counts, and transfer rate when downloading;
- an actionable bounded error when a check/download/install preparation fails.

Primary actions are state-dependent:

- `Check for updates`;
- `Download update`;
- `Update and restart`;
- `Retry` after recoverable errors.

Downloaded updates remain optional until the user explicitly presses `Update and restart`.

#### 4. Release workflow

A formal tag-release workflow owns production signing, notarization, update metadata, GitHub Draft Release creation, asset validation, and final publication.

Ordinary pull-request CI never receives production signing identities and never creates a public release.

#### 5. Platform signing identities

Windows uses Microsoft Artifact Signing / Trusted Signing Public Trust with one fixed publisher identity.

macOS uses one Developer ID Application identity plus Apple notarization credentials.

Formal credentials exist only in GitHub Actions trust/secrets and platform signing services. They are never copied into the application bundle.

## Trust boundaries

### Renderer boundary

The renderer is not an update authority.

It can request a state transition, but it cannot select what is downloaded or executed. The main process decides the update source and validates updater state before every operation.

Release notes are treated as untrusted display data. HTML from a GitHub Release is converted to bounded plain text before it reaches the renderer. No release-note script, inline handler, or arbitrary HTML is executed.

### Network boundary

The packaged application uses the public GitHub Releases provider generated into `app-update.yml` by the build system.

Application code must not call `setFeedURL` with renderer-controlled or settings-controlled data.

The stable repository identity is fixed to:

- owner: `chinatownlittlewhite`;
- repository: `webgpt-bridge`.

The updater does not need a GitHub token for public releases.

### Privilege boundary

The updater is not a privileged Windows host-preparation broker.

On Windows, an update enters the existing per-machine NSIS installation path. NSIS remains responsible for:

- installing below Program Files;
- repairing the fixed SYSTEM startup task;
- running the fixed host-prep `--apply` operation through the already-approved installer lifecycle;
- failing installation if privileged preparation cannot be established.

The updater itself never invokes `windows-host-prep --apply` or `--remove`.

## Version and channel model

### Desktop version authority

The root `package.json` `version` field is the sole desktop update version authority.

A formal release tag must be exactly:

`v${package.json.version}`

Example:

- package version: `0.3.5`;
- valid tag: `v0.3.5`.

The release workflow fails before signing if the tag and root package version differ.

`agent-runtime` retains its own internal component/protocol version and does not independently trigger desktop updates.

### Stable channel

The initial updater consumes only stable releases.

Prerelease versions such as `0.4.0-beta.1` and `0.4.0-rc.1` are not offered to stable clients.

`allowPrerelease` remains disabled.

### Downgrade policy

Downgrade remains disabled.

A running `0.4.0` client must not install `0.3.9` through this updater.

If a public release is defective, remediation is a higher version such as `0.4.1`; the contents of an already-public version are never silently replaced to simulate a rollback.

## Client update behavior

### Packaged-only activation

Real network update checks are enabled only when `app.isPackaged` is true.

Development/test mode uses an injected fake updater adapter for deterministic state-machine and IPC tests. Development mode must not query public GitHub Releases merely because a developer starts Electron locally.

### Startup check

After the application is ready and the main window/runtime initialization path is stable, the updater schedules a non-blocking check approximately 10 seconds later.

The startup check must not delay the main window or Bridge startup.

### Periodic check

After the startup check, automatic attempts are rate-limited to at most one check per six hours in a running application instance.

Automatic checks:

- do not download;
- do not install;
- do not stop Agent/tunnel processes;
- only update the UI state.

Manual `Check for updates` remains available between scheduled checks and is deduplicated if another check is already active.

### Download policy

`autoDownload` is explicitly disabled.

A transfer starts only after the user presses `Download update` for the version already selected by the updater.

While downloading, Bridge runtime functions remain available.

A duplicate download request while a transfer is active is rejected/deduplicated rather than creating a second transfer.

### Installation policy

A downloaded update is installed only after the user presses `Update and restart`.

Before invoking installation, the main process performs the normal orderly shutdown path for application-owned runtime activity:

1. stop the local Agent server;
2. stop the secure tunnel client;
3. close/terminate managed child processes through existing process lifecycle code;
4. persist settings/state that normal shutdown persists;
5. request platform update installation and relaunch.

If the Bridge cannot shut down its owned runtime safely, automatic installation does not proceed. The application reports a bounded retryable error and leaves the current version running.

On Windows, the per-machine NSIS upgrade may display UAC. UAC is an expected security boundary and must not be bypassed.

### Normal application exit

A downloaded update is not automatically installed merely because the user quits the app.

The updater is configured for explicit/manual install behavior.

### State machine

The normalized states are:

- `idle`;
- `checking`;
- `up_to_date`;
- `available`;
- `downloading`;
- `downloaded`;
- `installing`;
- `error`.

Only the main-process updater service changes state.

The renderer receives an immutable/bounded snapshot containing fields such as:

- `currentVersion`;
- `availableVersion`;
- `releaseDate`;
- `releaseNotes`;
- `downloadPercent` in `[0, 100]`;
- `downloadedBytes`;
- `totalBytes`;
- `bytesPerSecond`;
- `errorCode`;
- `errorMessage`;
- booleans describing which actions are enabled.

The state never exposes:

- signing credentials;
- raw HTTP authorization headers;
- local updater cache paths;
- downloaded installer paths;
- arbitrary GitHub response bodies.

### Error categories

The UI-facing error contract uses bounded categories:

- `network_unavailable`;
- `metadata_unavailable`;
- `metadata_invalid`;
- `download_failed`;
- `checksum_mismatch`;
- `signature_invalid`;
- `publisher_mismatch`;
- `shutdown_failed`;
- `install_launch_failed`;
- `unsupported_environment`.

The existing installed application remains usable after a check or download failure.

## Windows release and trust model

### Target

Windows remains x64 per-machine NSIS only.

The formal ZIP distribution remains unsupported while the privileged host-preparation architecture is required.

### Updater-compatible NSIS configuration

The Windows target remains NSIS and explicitly enables the elevate helper required by an updater that may service a per-machine installation.

The release configuration explicitly keeps update signature verification enabled.

### Artifact Signing

Formal Windows artifacts use Microsoft Artifact Signing / Trusted Signing with Public Trust.

The same validated publisher identity is used for every stable release so publisher reputation can accumulate across versions.

The implementation must use an Electron Builder version/toolset that supports the current Azure Trusted Signing integration. If the repository's existing Electron Builder version does not support the selected modern signing configuration, upgrading Electron Builder is part of implementation and must be covered by packaging regressions.

Formal build configuration defines one exact expected `publisherName` matching the certificate subject issued by the signing profile.

`verifyUpdateCodeSignature` remains enabled so `electron-updater` rejects a downloaded installer whose Authenticode publisher does not match the expected publisher embedded in build metadata.

### Signing scope

The release gate verifies signatures on at least:

- installed/main WebGPT Bridge executable;
- Windows sandbox native helper;
- Windows host-preparation native helper;
- final NSIS installer.

If Electron Builder does not automatically sign a nested native helper, a narrowly scoped build hook signs that exact packaged executable before the containing artifact is finalized.

Signing always occurs before final checksum/update metadata verification. A signed binary must never be modified afterward.

### Timestamp

Windows signatures use an RFC3161 timestamp service supported by the signing integration.

The release gate rejects missing/invalid signatures and missing expected publisher identity.

### SmartScreen expectation

The browser/SmartScreen acceptance criterion is:

- Windows shows the verified expected publisher rather than `Unknown Publisher`;
- every formal release uses the same publisher identity unless an explicitly planned certificate rotation occurs;
- release binaries are Authenticode signed and timestamped;
- unsigned formal GitHub Release executables are prohibited.

The project does not claim that first-time downloads from a new publisher can never receive SmartScreen reputation warnings. GitHub Releases remains the chosen distribution channel, so reputation is allowed to build over signed releases and downloads.

## macOS release and trust model

### Universal application

Formal macOS builds target `universal`, not arm64-only.

The release gate verifies that the main application executable contains both:

- `arm64`;
- `x86_64`.

A filename or workflow label containing `universal` is not sufficient evidence.

### Targets

Formal macOS releases contain both:

- DMG for normal user download;
- ZIP required by the macOS updater metadata/update path.

Both contain the same signed/notarized application version.

### Developer ID signing

The application uses a Developer ID Application identity from the Apple Developer Program.

Hardened Runtime remains enabled.

Entitlements remain minimal and explicit. Additional entitlements are added only when required by Electron/runtime behavior and covered by a release check. Broad entitlements that weaken library validation or runtime protection are not added merely to make signing easier.

### Notarization

Formal builds are notarized with Apple before publication.

CI uses App Store Connect API-key/notary credentials suitable for ephemeral runners rather than interactive Apple ID login.

Formal publication requires successful:

- code-sign verification;
- notarization submission result;
- stapling where supported for the distributed artifact/app;
- Gatekeeper assessment of the user-facing distribution artifact/application.

Failure leaves the GitHub Release in Draft state.

## CI credential model

### Pull-request CI

PR jobs receive no formal Windows or macOS signing credentials.

PR CI may create unsigned/test artifacts, but those artifacts:

- are never published as a stable GitHub Release;
- are never visible to the production updater;
- are clearly CI artifacts rather than trusted end-user releases.

PR CI retains the full Windows P0/AppContainer acceptance gate.

### Windows release identity

The release workflow uses GitHub OIDC / Azure workload identity where supported by the signing service integration rather than storing a long-lived Azure client secret.

The GitHub environment/repository variables identify the signing endpoint, signing account, certificate profile, and expected publisher. Secret/token material is not embedded in package configuration.

The Windows release job fails before publication if the configured Azure identity cannot sign or if the resulting publisher differs from the expected publisher.

### macOS release identity

macOS signing uses CI-provided Developer ID certificate/keychain material and notarization credentials.

Required formal release secrets/inputs are isolated to the macOS release environment. The repository never contains the certificate private key or App Store Connect private key in plaintext.

The release job fails closed when signing/notarization credentials are missing.

## GitHub Release workflow

### Trigger

A formal release workflow runs only for a tag matching `v*` and requires the tag to equal the root package version exactly.

A manually triggered ordinary build does not become a stable release unless it also satisfies the formal version/tag and release-gate rules.

### Draft-first publication

A GitHub Draft Release is the isolation boundary for a new version.

The sequence is:

1. validate tag/package version consistency;
2. run common Desktop and Agent regression gates;
3. create/find the exact Draft Release for the tag;
4. run Windows formal build/signing/acceptance;
5. upload Windows update assets to the Draft;
6. run macOS Universal build/signing/notarization/acceptance;
7. upload macOS update assets to the same Draft;
8. run a final release-asset validation gate;
9. publish the Draft as a stable GitHub Release only if every gate passes.

Draft releases are not treated as available stable updates by the client.

### Windows release assets

At minimum the Draft contains the Electron Builder artifacts required for the NSIS updater, including:

- signed NSIS installer;
- blockmap when generated/required;
- `latest.yml`;
- any user-facing checksum manifest produced by the project.

The final gate verifies metadata references only assets belonging to the same version.

### macOS release assets

At minimum the Draft contains:

- signed/notarized Universal DMG;
- signed/notarized Universal ZIP/update archive;
- `latest-mac.yml`;
- blockmap/update metadata when generated;
- any user-facing checksum manifest produced by the project.

### Release metadata validation

Before a Draft becomes public, CI verifies:

- root package version equals tag;
- every update metadata file reports the same version;
- referenced asset names exist in the Draft/validated artifact set;
- metadata hashes match the generated release assets;
- Windows Authenticode signature is valid and publisher matches exactly;
- Windows formal installer lifecycle smoke passes;
- macOS code signature is valid;
- macOS notarization/Gatekeeper checks pass;
- macOS main binary is truly Universal;
- no required platform asset is missing.

If any check fails, the Release remains Draft.

## Windows release acceptance

The formal Windows release job preserves the existing P0 gates and extends them for real updater/install lifecycle behavior.

Required evidence includes:

1. native helpers build successfully;
2. host-prep initial apply is idempotent;
3. remove makes the product capability ACE missing;
4. reapply repairs readiness;
5. standard non-admin AppContainer acceptance passes;
6. `cmd`, `git`, `dotnet`, `node`, and supported `gh` compatibility smokes pass;
7. real per-machine NSIS artifact installs below Program Files;
8. the installed privileged helper exists only at the expected protected path;
9. the fixed host-preparation scheduled task has SYSTEM principal, highest run level, boot trigger, exact protected executable, and fixed `--apply` argument;
10. installed host preparation is `ready`;
11. uninstall removes the scheduled task, installed privileged payload, and product capability ACE;
12. signed formal artifacts pass publisher/timestamp validation.

Before the updater feature is considered release-ready, a packaged updater E2E must exercise an old-release-to-new-release installed upgrade using two test release versions or an isolated test feed, without exposing that feed as a production renderer setting.

## macOS release acceptance

Required evidence includes:

1. desktop tests pass;
2. Universal build completes;
3. the main executable contains `arm64` and `x86_64` slices;
4. `codesign` verification succeeds for the application and nested executable code;
5. Developer ID identity is the expected release identity;
6. notarization succeeds;
7. stapling/Gatekeeper verification succeeds for the distributed form where applicable;
8. DMG and ZIP/update assets exist for the same version;
9. `latest-mac.yml` references the correct version/assets;
10. a packaged updater smoke can read update metadata without requiring a GitHub token.

Before the updater feature is considered release-ready, a packaged updater E2E verifies an installed old signed/notarized version can download, install, relaunch, and report the new `app.getVersion()`.

## Update E2E acceptance

Before the update feature is considered release-ready, tests cover the full state machine using a fake updater adapter and at least one packaged-platform integration path.

Required deterministic tests include:

- idle -> checking -> up_to_date;
- idle -> checking -> available;
- available -> downloading -> downloaded;
- downloaded -> orderly shutdown -> installing;
- network error -> error -> retry;
- checksum/signature/publisher error -> fail closed;
- duplicate check/download requests are deduplicated;
- prerelease is not offered to stable users;
- downgrade is rejected;
- normal application quit does not install a downloaded update;
- renderer cannot provide URL/path/repository/installer arguments;
- release notes are normalized to bounded plain text.

Formal platform release acceptance then validates real signatures and real installation behavior that fake updater tests cannot prove.

## Rollback and failed releases

### Before publication

A broken Draft Release is not visible to stable clients.

The workflow may replace/re-upload assets in the Draft while fixing the release candidate, provided the Draft has never been published and final validation is rerun.

### After publication

A public version is immutable from the updater's point of view.

If `v0.3.5` is defective after users install it:

- do not replace it with different `v0.3.5` binaries;
- do not force downgrade users to `v0.3.4`;
- publish a higher corrective version such as `v0.3.6`.

The first implementation does not use staged rollout. The metadata/release architecture must not prevent adding a staged percentage in a later design.

## Browser and OS warning acceptance

### Windows

The release goal is a trusted, consistently signed publisher experience, not an unverifiable promise of zero SmartScreen reputation prompts.

Acceptance requires:

- Authenticode valid;
- expected publisher visible;
- stable publisher across releases;
- timestamp present;
- no unsigned formal executable assets.

### macOS

Acceptance requires:

- Developer ID signature valid;
- Hardened Runtime active;
- notarization success;
- Gatekeeper assessment succeeds for formal distribution.

## Observability

Updater logs are written through the existing local desktop logging/audit style with redaction and bounded messages.

Logs may include:

- updater state transition;
- current/available version;
- check/download timing;
- download percentage summary;
- normalized error category;
- install/restart request result.

Logs must not include signing credentials, GitHub authorization headers, Apple API private keys, Azure tokens, or raw secret environment values.

## Files and implementation areas

Expected implementation areas include:

- root `package.json` / lockfile for `electron-updater`, publish/signing/build configuration, true Universal target, and updater-compatible NSIS options;
- a focused updater service under `src/` rather than embedding updater state inside the already-large host lifecycle code;
- `src/main.cjs` for lifecycle integration and narrow IPC registration;
- `src/preload.cjs` for bounded renderer bridge methods/events;
- `src/renderer/index.html`, `renderer.js`, and `styles.css` for update UI;
- desktop tests for updater state, IPC boundary, package config, release workflow, Universal configuration, and signing gates;
- a formal tag release workflow separate from or clearly isolated inside the ordinary build workflow;
- explicit macOS entitlements/signing resources only where required;
- release validation scripts that can be run locally/CI without embedding credentials.

## External prerequisites

Formal public releases cannot satisfy the signing/trust requirements until the repository owner configures:

### Windows

- Microsoft Artifact Signing / Trusted Signing Public Trust account;
- certificate profile;
- verified publisher identity;
- GitHub-to-Azure release identity with signing role;
- repository/environment variables identifying endpoint/account/profile/expected publisher.

### macOS

- active Apple Developer Program membership;
- Developer ID Application certificate/private key available to the protected release environment;
- Apple Team ID;
- App Store Connect/notarization API credentials available only to the release environment.

Implementation may be completed before these identities are provisioned, but the formal release workflow must fail closed rather than publish unsigned/unnotarized stable assets.

## Security invariants

1. Public updater source is fixed to the official GitHub repository.
2. Renderer input can never select a URL, executable, installer, repository, publisher, or release channel.
3. Stable client never receives prerelease by default.
4. Downgrade is disabled.
5. Auto-download is disabled.
6. Auto-install-on-normal-quit is disabled; install is explicit.
7. Windows update signature verification remains enabled.
8. Windows publisher identity is fixed and verified before release.
9. macOS formal release is signed and notarized.
10. Formal signing secrets are unavailable to PR jobs and packaged clients.
11. The updater never performs Windows null-device or scheduled-task mutation directly.
12. A release becomes public only after both platform release gates pass.
13. Published release versions are not silently replaced to emulate rollback.
14. Existing installed version remains usable after update check/download failure.

## Acceptance summary

The feature is complete only when all of the following are true:

- Windows and macOS packaged applications show current version and in-app update controls;
- stable GitHub Release detection works without a client GitHub token;
- user-controlled download progress works;
- explicit update-and-restart works on both platforms;
- normal quit does not force-install a pending update;
- Windows per-machine update preserves the approved host-prep/Program Files/SYSTEM-task security lifecycle;
- Windows formal artifacts are signed by the expected stable publisher and verified before publication;
- macOS is truly Universal, Developer ID signed, notarized, and Gatekeeper-valid;
- release metadata/checksums match the exact uploaded artifacts;
- an incomplete platform build leaves the release Draft and invisible to stable clients;
- the existing Windows P0 acceptance remains a hard release gate;
- public tool/Agent security boundaries are unchanged by the updater feature.

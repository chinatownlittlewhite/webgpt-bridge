# WebGPT Bridge v0.5 Security, Reliability, Slimming, and UI Design

## Status

Approved direction on 2026-08-29. Baseline is Desktop v0.4.11 / Agent Runtime v0.9.3 at commit `05e9faf192fa8d6341f991d99e15deb68a2b1338`.

This document is the design baseline for the next major internal hardening cycle. It preserves all externally useful v0.4.11 behavior while changing internal authorization, persistence, Host composition, packaging, diagnostics, and renderer information architecture.

Existing v0.4.9/v0.4.10 failed release tags and the published v0.4.11 release remain immutable.

## Hard constraints

1. Existing users upgrade without resetting settings, runtime keys, workspace selection, handoff data, or valid Goal state.
2. Existing MCP capabilities are not removed merely to simplify implementation or reduce package size.
3. Existing shell, privilege-escalation, sensitive-path, sandbox, approval, and process-isolation boundaries are never weakened.
4. macOS and Windows remain formal release targets with real packaged acceptance.
5. A macOS Universal artifact remains available. Architecture-specific arm64 and x64 artifacts may be added as smaller alternatives.
6. Renderer modernization stays dependency-light: HTML, CSS, and vanilla JavaScript unless a later independently approved requirement makes a framework necessary.
7. Slimming must preserve offline-complete operation of the packaged product; required security/runtime components are not deferred to first-run downloads.
8. Existing App identity and user-data compatibility are preserved unless an explicit migration with compatibility proof is later approved.
9. Changes land incrementally with regression gates. No big-bang rewrite of Desktop or Agent Runtime is permitted.

## Goals

- Close the current known-folder authorization bypass by making Host file access capability-scoped rather than blacklist-driven.
- Guarantee one active Desktop owner for one profile and prevent concurrent ownership of settings, fixed ports, broker state, and Goal persistence.
- Add authenticated/versioned App-owned broker sessions.
- Collapse duplicated Desktop/Agent authorization logic into one canonical security-policy core with adapters.
- Replace manually synchronized tool-name/dispatch/capability lists with one canonical tool registry.
- Strengthen Goal persistence from atomic JSON replacement to recoverable journaled transactions with explicit crash semantics.
- Make local staged file batches recoverable across App/process crashes.
- Generalize Goal verification for code changes, read-only audits, and system operations without weakening strict completion gates.
- Reduce `src/main.cjs` to an Electron composition root while retaining already working focused services.
- Reduce packaged size without reducing runtime or security behavior.
- Redesign the Desktop UI as a clear native utility focused on status, workspace, permissions, updates, and diagnostics.
- Expose trusted build/runtime/version facts directly instead of requiring filesystem inspection.

## Non-goals

- No replacement of Electron in this cycle.
- No React/Vue/Tailwind migration.
- No switch to a cloud-required runtime or first-run dependency download.
- No UPX or similar executable packer that materially increases AV/signing/runtime risk.
- No broad arbitrary Host filesystem, process, registry, shell, or network introspection API.
- No automatic deletion of user-authored handoff data or historical Goal evidence merely for cosmetic cleanup.
- No relaxing strict verification to make Goal completion easier.
- No unrelated product-feature expansion while this architecture cycle is in progress.

## Delivery strategy

Use incremental internal replacement rather than a rewrite.

The sequence is security boundary first, durable state second, shared contracts third, Host decomposition fourth, packaging fifth, renderer sixth, then full migration and packaged acceptance.

Each stage must leave the branch in a testable state and preserve the v0.4.11 external contract unless that stage explicitly introduces a backward-compatible additive capability.

## 1. Host file capabilities

### Current problem

`local_list_known_folder` and `local_read_known_folder` require explicit authorization for Desktop, Downloads, and Documents, but generic `local_list` / `local_read` accept absolute paths. The current path classifier mainly excludes known sensitive/system roots; therefore a known-folder prompt can be bypassed when the absolute path is known.

More broadly, blacklist-based Host-read authorization cannot enumerate every future credential-bearing location.

### Target model

Host access is capability-scoped.

- Workspace access is an implicit scoped capability created from the configured workspace boundary.
- Desktop, Downloads, and Documents are protected known-folder roots. Generic broker access to those roots must require the same authorization capability as the dedicated known-folder tools.
- Other non-workspace Host paths are not globally readable by default. They require an explicitly granted path capability.
- Sensitive reads use single-use capabilities and remain read/list only.
- Sensitive writes/execution remain denied.
- System roots remain denied regardless of approval preset.
- Symlink/reparse-point escape remains forbidden.

A capability is bound to at least:

- canonical root/path,
- operation class,
- issuance generation/session,
- expiry or use count,
- security-policy version.

A capability cannot expand its own scope and cannot be supplied by the model as an arbitrary self-minted string.

### Backward compatibility

Existing MCP method names remain available. Generic Host read/list behavior outside the workspace may become more restrictive where the previous behavior relied on implicit broad Host access; this is an intentional security correction, not a removed supported contract.

Dedicated known-folder behavior remains available and becomes the canonical path for those roots.

## 2. Desktop single-instance ownership

Acquire Electron's single-instance lock before starting runtime-owned services.

The primary instance owns:

- settings mutation,
- runtime-key migration/write,
- local broker socket/pipe,
- Agent and Tunnel children,
- fixed local ports,
- update lifecycle,
- active Goal writer lifecycle.

A secondary instance must not initialize those resources. It activates/focuses the primary window and exits.

This creates the product-level ownership invariant:

`one Desktop profile -> one broker owner -> one Agent owner -> one persistent Goal writer`.

The Agent's existing single-writer Goal mutation protection remains necessary inside that owner; the Desktop lock does not replace Agent-level serialization.

## 3. Authenticated and versioned local broker

The App-owned Unix socket / named pipe remains the transport, but OS-user access is no longer the only authentication boundary.

At each primary Desktop start:

1. Generate a cryptographically random broker session secret.
2. Pass it only to the spawned Agent through trusted child configuration/environment.
3. Require a broker handshake before normal methods.
4. Bind accepted connections to the negotiated session.

Handshake fields include:

- broker protocol version,
- Desktop product/runtime version,
- Agent runtime version,
- random session authentication proof,
- supported broker method/capability set.

Unknown protocol generations fail with a stable compatibility error. Authentication failure reveals no secret and exposes no broker methods.

Secrets are not written to logs, capabilities responses, project files, handoff, or diagnostic snapshots.

## 4. Canonical Security Policy Core

### Problem

Authorization semantics currently live in multiple layers including Agent command policy, Desktop local policy, terminal approval, SSH validation, and approval-prompt interpretation. Tests reduce drift but do not eliminate duplicated policy truth.

### Design

Create a pure, dependency-light policy core that consumes a normalized operation descriptor and returns a normalized authorization decision.

Representative input dimensions:

- operation kind,
- resource type and normalized scope,
- workspace relationship,
- sensitivity class,
- network/external-write class,
- executable/command class,
- sandbox verification state,
- requested sandbox expansion,
- granted capability set,
- user approval preset.

Representative result:

- `allow`, `confirm`, or `deny`,
- stable rule id,
- human-readable reason,
- permission class,
- remember scope where permitted.

Desktop and Agent adapters may perform platform-specific normalization, but they must not reinterpret a core `deny` into `confirm/allow` or independently recreate the same policy table.

### Approval presets

Keep the user-facing presets for continuity:

- cautious,
- development,
- auto,
- full_control.

Internally map them to a capability/permission matrix such as workspace read/write, host read/write, network, remote write, execution, sensitive read, and sandbox expansion.

`full_control` remains a high-autonomy preset, not a bypass around immutable denies, sensitive access, shell disablement, privilege escalation, or unverified sandbox expansion.

## 5. Goal Store v2

### Problem

The v0.4.11 file store uses temp-file write plus rename. This avoids most partial-JSON states but does not justify full power-loss durability semantics and has no cross-process WAL.

### Design

Introduce a versioned journal + snapshot store implemented with standard Node filesystem primitives to avoid a new native database ABI/package burden.

Representative layout under the existing internal state boundary:

```text
.webgpt-handoff/
  goals/
    state-v2/
      metadata.json
      snapshot.json
      journal.log
```

Critical mutation protocol:

1. Append intent record with monotonic sequence and mutation id.
2. Flush/synchronize durable intent before protected effect where durable intent is required.
3. Perform the protected effect.
4. Append result/commit record.
5. Flush commit.
6. Periodically publish a compact snapshot atomically.
7. Compact only after the new snapshot and retained journal boundary are confirmed durable.

Records bind at least:

- store/schema version,
- sequence,
- mutation id,
- Goal session id,
- operation,
- input hash or bounded canonical mutation identity,
- state/result class,
- timestamp,
- integrity checksum.

Startup replays only a valid contiguous journal suffix over a valid snapshot. Corrupt, discontinuous, or uncertain protected mutations fail closed. No automatic replay of a possibly completed external effect is permitted.

### v1 migration

Existing `.webgpt-handoff/goals/*.json` state is imported transactionally.

Migration rules:

1. Read and validate v1 sessions without deleting them.
2. Build v2 snapshot/journal state in a temporary migration target.
3. Re-open and validate v2 state.
4. Atomically mark v2 migration complete.
5. Preserve old files until successful migration is proven; later cleanup is a separate safe housekeeping concern.

A migration failure leaves v1 readable and never silently creates an empty Goal history.

## 6. Crash-recoverable local file batches

### Problem

The existing in-memory rollback journal handles ordinary exceptions but not a process/OS crash between rename operations.

### Design

Each staged commit uses an on-disk transaction directory on the same relevant filesystem whenever atomic rename semantics are required.

Representative contents:

```text
.webgpt-bridge-txn-<id>/
  transaction.json
  new/
  backup/
```

Persisted states include:

- prepared,
- applying,
- committed,
- rolling_back.

The manifest records exact paths, expected SHA-256 preconditions, operation order, and recovery state without secret file contents in logs/diagnostics.

On startup/broker initialization, recover only transaction directories matching WebGPT Bridge's strict format and boundary rules.

- `prepared`: safely roll back/cleanup.
- `applying`: reconcile manifest and filesystem, preferring restoration over guessing success.
- `committed`: verify final state then cleanup.
- corrupt/ambiguous: fail closed and surface actionable diagnostics rather than destructive guessing.

Recovery must preserve the existing SHA-precondition guarantees and must not follow attacker-created symlinks/reparse points.

## 7. Goal verification profiles

Add explicit verification profiles while preserving the current strict default for existing callers.

### `code-change`

Use project checks when available/required: test, lint, typecheck/check/build as configured, acceptance criteria, and optional trusted verifier. Code mutations cannot claim completion solely from self-report.

### `read-only-audit`

Require evidence that the Goal performed no tracked mutation, left no owned process running, and satisfied its acceptance criteria. When a Git repository is available, unchanged working-tree evidence may strengthen verification. Lack of a project test script alone is not a failure for a genuinely read-only audit.

### `system-operation`

Require an explicit postcondition or trusted verifier appropriate to the operation. The absence of project tests never implies success.

Existing Goal requests without a profile retain legacy strict code-project semantics until an explicit compatibility migration is introduced.

Capabilities expose supported profiles and effective profile for each Goal session.

## 8. Canonical Tool Registry

### Problem

Tool names, schemas, broker methods, Goal eligibility, capability reporting, and dispatch currently have multiple manually synchronized representations.

### Design

Define a canonical registry/descriptor source with fields including:

- public tool name,
- description,
- input schema,
- implementation adapter,
- broker method if applicable,
- Goal eligibility,
- timeout class,
- security/side-effect metadata,
- capability category.

Generate or derive from that registry:

- MCP registration,
- `get_capabilities` tool lists,
- Goal-eligible tool subsets,
- App-owned broker dispatch validation,
- contract-test expectations.

The broker server remains authoritative for Host-side authorization even when the Agent advertises a tool.

Capabilities distinguish at minimum:

- all effective tools,
- Goal tools,
- broker tools.

## 9. Host decomposition

The existing v0.4.11 focused components such as RuntimeSupervisor, UpdateService, file broker, lifecycle coordinator, and policy helpers are retained where correct.

`src/main.cjs` becomes a composition root and should no longer contain most business/security implementations.

Target ownership boundaries may include:

```text
src/host/
  settings-store.cjs
  secret-store.cjs
  single-instance.cjs
  broker-server.cjs
  host-security.cjs
  health-service.cjs
  runtime-host.cjs
  runtime-processes.cjs
  ipc-controller.cjs
  window-controller.cjs
  tray-controller.cjs
  diagnostics-service.cjs
```

Exact filenames are implementation details; the required design boundary is that each module has one clear ownership responsibility and can be tested without booting the whole Electron App.

`main.cjs` should primarily:

1. establish App/profile ownership,
2. construct services,
3. wire dependencies and IPC,
4. create UI/tray,
5. coordinate start/shutdown.

No refactor is accepted merely for line-count reduction; behavior and tests must improve or remain equivalent.

## 10. Package slimming

### Baseline

The locally inspected macOS application from the current build is approximately:

- app total: 370 MiB,
- Electron Frameworks: 215 MiB,
- Resources: 156 MiB,
- tunnel resources: 121 MiB,
- unpacked Agent payload: 32 MiB,
- `app.asar`: 2.1 MiB,
- renderer source: about 21 KiB.

The major opportunities are runtime/framework/native payloads, not business JavaScript.

### Rules

- Do not remove functional/security fallbacks solely for size.
- Do not introduce first-run network dependency installation.
- Do not use UPX.
- Pruning happens before signing/notarization.
- Any executable stripping is followed by artifact/runtime acceptance and signing verification.

### macOS artifacts

Continue publishing a Universal artifact and add architecture-specific alternatives when release CI supports them safely:

- macOS Universal,
- macOS arm64,
- macOS x64.

Architecture-specific packages include only required target native payloads. Universal includes both Darwin architectures where required.

### Agent/native pruning

Production packaging should exclude target-irrelevant payloads such as non-target native binaries, tests, examples, development-only metadata, and source maps only after confirming they are not required for runtime diagnostics.

Windows continues to bundle its trusted Node runtime because that is part of the current compatibility/security contract.

### Tunnel payload

Measure `cloudflared` and `tunnel-client` independently. If supported toolchains can safely strip symbols without changing signed/runtime behavior, do so before signing and rerun tunnel/package acceptance. Do not replace them with remote on-demand downloads in this cycle.

### Size budget

Release CI records component sizes and compares them with the previous formal release. Report at least:

- total artifact/unpacked app,
- Electron/framework portion where measurable,
- Agent runtime,
- tunnel payload,
- Node runtime on Windows,
- node-pty/native payload,
- `app.asar`.

Unexpected material growth must be attributable in release verification rather than silently accepted.

## 11. Desktop UI redesign

### Product direction

Keep the renderer a native-feeling desktop utility rather than a web dashboard. Continue local HTML/CSS/vanilla JS, system fonts, no remote fonts/assets, and no new heavy UI framework.

### Information architecture

Use five logical views/sections:

1. Overview
2. Workspace
3. Permissions
4. Advanced
5. Diagnostics

This may be implemented as a compact sidebar/navigation or equivalent native utility pattern, but must remain keyboard-accessible and usable at the supported minimum window size.

### Overview

Prioritize current operational truth:

- Connected/Offline/Degraded state,
- Desktop version,
- Agent version,
- workspace,
- ChatGPT <-> Tunnel <-> Agent path,
- Agent/Tunnel/Sandbox/GitHub health,
- primary Start/Stop/Open ChatGPT actions,
- update state when actionable.

A user should not have to infer connectivity from several unrelated text fields.

### Workspace

Expose normal setup fields without mixing them with advanced runtime internals:

- workspace directory,
- Tunnel ID,
- runtime key state,
- profile.

### Permissions

Show the effective policy as a readable matrix in addition to the existing preset name. Example classes:

- Workspace files,
- Host files,
- Network,
- Remote write,
- Sensitive files,
- Shell,
- Privilege escalation,
- Sandbox expansion.

The UI must make immutable denies obvious so `full_control` cannot be misread as unrestricted machine control.

### Advanced

Contain expert-only settings such as custom runtime path, custom tunnel-client, Node path, proxy, SSH, and design-issue journal.

### Diagnostics

Expose trusted, bounded product-owned state:

- Desktop version/build identity,
- Agent version,
- MCP protocol revision,
- broker protocol version,
- sandbox state,
- tunnel readiness,
- GitHub CLI connectivity/binary/auth states,
- Goal store version/migration health,
- verification profiles,
- bounded logs.

Windows Desktop-version verification must no longer require reading a protected install directory.

### Visual design

Preserve the existing dark-ink/mint brand language while improving hierarchy:

- fewer decorative borders,
- stronger whitespace and grouping,
- compact status indicators,
- system font stack,
- platform-appropriate window behavior,
- light/dark appearance support where feasible without introducing a framework,
- visible keyboard focus,
- reduced-motion support,
- no remote visual resources.

## 12. Host responsiveness and logs

### GitHub health

Replace synchronous main-thread `gh auth status` health probing with bounded asynchronous execution so a slow/broken CLI cannot freeze the Electron UI thread.

Connectivity, binary presence, and authentication remain distinct states.

### Logs

Use the already established bounded Host log truth but deliver normal updates incrementally rather than retransmitting the full ring on every new line.

Protocol includes a bounded initial snapshot plus monotonic append batches. Renderer detects generation/sequence gaps and requests one bounded resync.

The renderer owns only a bounded presentation buffer; Host remains authoritative.

## 13. Capabilities and diagnostics contract

`get_capabilities` and trusted Desktop diagnostics should expose compatible facts from the same underlying product metadata rather than each inventing version strings.

Additive fields include where available:

- Desktop version,
- Agent version,
- MCP protocol revision,
- broker protocol version,
- Goal store version,
- supported Goal verification profiles,
- all tools,
- Goal tools,
- broker tools.

Do not expose runtime secrets, bearer tokens, proxy credentials, raw environment, broker secret/socket path, or unrestricted Host paths.

## 14. macOS privacy/network metadata hardening

The next packaging pass must explicitly verify generated `Info.plist` rather than accepting broad defaults.

- Remove Camera/Microphone/Audio/Bluetooth usage descriptions unless a shipped feature demonstrably requires them.
- Remove `NSAllowsArbitraryLoads` if local/tunnel functionality works with narrower ATS/local-network configuration.
- Preserve only the minimum exceptions needed for actual local WebGPT Bridge operation.

This is a packaging-security requirement and is verified on the final artifact, not merely in source config.

## 15. Migration compatibility

Formal migration tests begin from representative v0.4.11 state and prove:

- settings load without manual reset,
- encrypted runtime key remains readable under the same App/user-data identity,
- workspace selection is preserved,
- handoff bundle is not overwritten destructively,
- Goal v1 sessions migrate or remain safely recoverable,
- unknown future/invalid persisted data fails closed with diagnostics,
- updater can transition an installed prior release to the candidate build without orphaning the runtime.

No migration may interpret missing new fields as permission expansion.

## 16. Error and recovery model

New cross-subsystem errors use stable machine-readable codes plus bounded human-readable detail. Representative classes include:

- `SECONDARY_INSTANCE`,
- `BROKER_AUTH_FAILED`,
- `BROKER_PROTOCOL_MISMATCH`,
- `HOST_CAPABILITY_REQUIRED`,
- `HOST_CAPABILITY_EXPIRED`,
- `GOAL_STORE_CORRUPT`,
- `GOAL_STORE_RECOVERY_UNCERTAIN`,
- `GOAL_STORE_MIGRATION_FAILED`,
- `FILE_TRANSACTION_RECOVERY_REQUIRED`,
- `FILE_TRANSACTION_AMBIGUOUS`,
- `VERIFICATION_PROFILE_UNSUPPORTED`.

Errors must not leak secrets or become authorization oracles beyond the information needed to repair the product state.

## 17. Acceptance gates

### Security

- Generic `local_read/local_list` cannot bypass Desktop/Downloads/Documents authorization.
- Arbitrary Host reads require a scoped capability outside the workspace.
- System/sensitive immutable denies remain enforced under `full_control`.
- Shell and privilege escalation remain model-disabled.
- Unverified or expanded sandbox access still follows the intended confirmation boundary.
- Broker rejects missing/invalid authentication and unsupported protocol versions.
- Capability tokens cannot be replayed outside their intended session/scope.

### Persistence

Fault-injection tests cover at minimum:

- before intent durable write,
- after durable intent / before protected effect,
- during/after protected effect,
- before durable commit,
- during snapshot publication/compaction.

Restart recovery must never silently replay an uncertain external effect.

File-batch recovery tests cover crash states around each rename/manifest transition and verify no silent data loss.

### Goal verification

- `code-change` retains strict project verification.
- `read-only-audit` can complete without nonexistent project tests only when mutation/process/evidence invariants pass.
- `system-operation` requires a trusted postcondition/verifier.
- Legacy profile behavior remains backward compatible.

### Contracts

- Tool registry-derived names match actual MCP registration.
- Broker dispatch accepts exactly the registered broker methods.
- Capabilities distinguish total/Goal/broker tools.
- Desktop and Agent policy adapters agree on canonical rule ids for shared operations.

### Host lifecycle

- Second Desktop instance never starts or mutates runtime-owned resources.
- Stop/Quit/Update continue to leave no known orphan runtime children.
- Broker session secret rotates with the primary App lifecycle.

### UI

Existing user actions remain available: load/save settings, start, stop, clear key, choose paths, open ChatGPT, update check/download flow as supported, proxy, SSH, permissions, and logs.

Status UI renders connected/degraded/offline from authoritative Host state and remains keyboard usable.

### Size

- Architecture-specific macOS package is measurably smaller than Universal.
- No size optimization removes a capability or required runtime check.
- CI emits a reproducible component-size report.
- Any final size regression is explained before formal release.

### macOS

- Seatbelt remains verified.
- arm64/x64/Universal native payloads are correct for each artifact.
- final `Info.plist` contains only justified privacy/ATS declarations.
- packaged PTY, tunnel, updater, shutdown, and Goal smoke tests remain green.

### Windows

- AppContainer remains verified.
- bundled Node and Windows host preparation remain correct.
- broker auth/versioning works over named pipe.
- installer/update, PTY, tunnel, shutdown, and Goal smoke tests remain green.

## 18. Implementation order

The implementation plan must preserve this dependency order unless a failing test proves a narrower prerequisite is needed:

1. Establish v0.4.11 regression and component-size baselines.
2. Close Host/known-folder capability boundaries.
3. Add Desktop single-instance ownership.
4. Add broker session authentication and protocol versioning.
5. Introduce the canonical Security Policy Core and migrate existing adapters without changing intended decisions.
6. Implement Goal Store v2 and v1 migration.
7. Implement crash-recoverable local file transactions.
8. Add Goal verification profiles.
9. Introduce the canonical Tool Registry and derive capabilities/Goal/broker tool sets.
10. Decompose `main.cjs` around the now-stable ownership boundaries.
11. Prune target-irrelevant package/native payloads.
12. Add macOS Universal + arm64 + x64 release variants and size budgets.
13. Redesign renderer information architecture and visuals.
14. Add/finish diagnostics, asynchronous GitHub health, and incremental log delivery.
15. Run full migration, cross-platform packaged acceptance, release audit, and exact-artifact verification.

## 19. Completion definition

This architecture cycle is complete only when all of the following are true on the same candidate commit:

- Desktop and Agent full test suites are green.
- Security and crash-recovery fault-injection suites are green.
- v0.4.11 migration fixtures succeed without manual reset.
- macOS packaged acceptance succeeds for required architecture variants and Universal release remains supported.
- Windows packaged/installer acceptance succeeds.
- final capabilities/tool/policy contracts are self-consistent.
- package-size report is produced and no unexplained material regression remains.
- redesigned UI preserves all required operational controls and diagnostics.
- release metadata and artifacts identify the exact candidate commit.

Formal release/tag publication is a later implementation/release step. This design document does not mutate or replace the published v0.4.11 release.

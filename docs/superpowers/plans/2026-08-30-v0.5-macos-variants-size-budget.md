# macOS Variants and Size Budget Implementation Plan

> **Implementation status:** Product work is complete on the Step 12 task branch; final cross-platform package verification and integration are tracked below.

**Goal:** Publish and verify macOS arm64, x64, and Universal packages while keeping Universal as the updater target and recording attributable package-size growth.

**Architecture:** macOS distribution is orchestrated explicitly in the fixed order `arm64 -> x64 -> universal`. Each build receives `WEBGPT_MAC_PACKAGE_VARIANT`, and the matching Tunnel payload is prepared immediately before Electron Builder. The `afterPack` hook normalizes/prunes node-pty so single-architecture packages retain only their required Darwin native payload while Universal retains both. The Universal build runs last so `latest-mac.yml` remains the updater source. Component size verification is part of the macOS distribution orchestrator and runs only after all three packages exist.

**Tech Stack:** Node.js 22+, Electron Builder 26.15.3, node:test, GitHub Actions, macOS `lipo`.

**Spec:** `docs/superpowers/specs/2026-08-29-v0.5-security-architecture-slim-ui-design.md`

## Global Constraints

- Continue publishing a macOS Universal artifact.
- Add macOS arm64 and macOS x64 alternatives.
- Architecture-specific packages include only required target native payloads; Universal retains both Darwin architectures where required.
- Do not introduce first-run network dependency installation.
- Do not use UPX.
- Pruning happens in `afterPack`, before any signing/notarization stage.
- Release verification records total app, frameworks, resources, `app.asar`, unpacked app, Agent runtime, node-pty, Agent native payload, Tunnel payload, and Windows bundled Node runtime sizes.
- Unexpected material growth fails closed against the committed previous-formal-release baseline.
- `latest-mac.yml` remains bound to the Universal updater ZIP.

### Task 4: Record component sizes and enforce attributable growth

**Implemented size contract:**
- `collectPackageSizes(appRoot)` records `totalBytes`, `frameworksBytes`, `resourcesBytes`, `appAsarBytes`, `appAsarUnpackedBytes`, `agentRuntimeBytes`, `nodePtyBytes`, `agentNativeBytes`, `tunnelClientBytes`, and `windowsNodeRuntimeBytes`.
- `build/package-size-baseline.json` identifies previous formal release `v0.4.11` and includes all four package variants (`mac-arm64`, `mac-x64`, `mac-universal`, `win-x64`). Historical single-architecture macOS packages did not exist, so their initial baseline uses the previous Universal envelope conservatively rather than inventing smaller historical measurements.
- `evaluateSizeBudget()` fails closed on missing/invalid metrics and rejects component growth above `max(5%, 5 MiB)` relative to the committed baseline.
- macOS distribution writes three `release/package-size-*.json` reports and checks the budget only after all three builds; Windows writes/checks `release/package-size-win-x64.json` after packaging.

# Goal Verification Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add explicit `code-change`, `read-only-audit`, and `system-operation` Goal verification profiles while preserving legacy strict code-project behavior for callers that omit a profile.

**Architecture:** Add a small pure profile helper that owns profile names plus Goal-action side-effect classification. Persist the effective profile and optional system postcondition inside each Goal session; keep legacy sessions mapped to an internal `legacy-code-project` profile. `goal_finish` selects profile-specific completion evidence while retaining acceptance-criteria gating and the existing trusted completion verifier.

**Tech Stack:** Node.js ESM, MCP JSON schemas, existing Goal controller/store v2, Node test runner.

**Spec:** `docs/superpowers/specs/2026-08-29-v0.5-security-architecture-slim-ui-design.md` section 7.

## Global Constraints

- Existing Goal requests without an explicit verification profile retain legacy code-project semantics.
- Explicit supported profiles are exactly `code-change`, `read-only-audit`, and `system-operation`.
- `code-change` uses configured project checks and cannot complete after side-effecting Goal actions solely from model self-report.
- `read-only-audit` must never invoke a side-effecting Goal action and must not require a project test script merely to complete a genuine audit.
- `system-operation` requires an explicit persisted postcondition with bounded finish evidence or a trusted completion verifier; missing project tests never count as verification.
- Acceptance criteria remain mandatory for every profile when configured.
- Existing Goal v2 persistence, pause/resume, mutation durability, budgets, approval boundaries, sandboxing, workspace scope, and 26-tool surface remain compatible.
- Capabilities advertise supported explicit profiles and the legacy default; each session view exposes its effective profile.
- Do not implement the Canonical Tool Registry in this phase.

### Task 3: Profile-specific completion verification

**Files:**
- Modify: `agent-runtime/src/goal-controller-core.js`
- Modify: `agent-runtime/test/goal-controller.test.js`
- Modify: `agent-runtime/test/goal-mode.test.js`

**Interfaces:**
- `finish()` accepts `postconditionEvidence` as an optional bounded string.
- The existing acceptance-criteria check always runs first for every profile.
- Legacy verification behavior remains byte-for-byte equivalent in outcome ordering: configured project checks, optional trusted verifier, then global `strictVerification`.
- Explicit `code-change`: run configured project checks exactly as legacy does; if `sideEffectActionCount > 0`, completion requires at least one successful project check or a successful trusted verifier even when global `strictVerification` is false.
- `read-only-audit`: skip project tasks, require `sideEffectActionCount === 0`, and mark the structural read-only check as verification evidence. A supplied trusted verifier still runs and may reject completion.
- `system-operation`: skip project tasks. Completion requires either `(postcondition && postconditionEvidence)` or a successful trusted verifier. A supplied trusted verifier still runs and may reject. Missing tests do not imply success.
- Pass `verificationProfile`, `postcondition`, and `postconditionEvidence` to trusted `verifyCompletion`.

- [ ] **Step 1: Write failing profile completion tests**

Add focused tests proving:

1. Explicit `code-change` with an invoked side-effecting tool and no available project check/verifier returns `continue_required` even when `strictVerification: false`.
2. Explicit `code-change` completes when a real configured project check succeeds.
3. Legacy omitted profile preserves the current behavior when project tasks are unavailable and strict verification is false.
4. `read-only-audit` completes after only read-only inspection actions without invoking `run_project_task`.
5. `read-only-audit` cannot complete if a hydrated/test session has nonzero `sideEffectActionCount`.
6. `system-operation` with neither postcondition evidence nor trusted verifier returns `continue_required`.
7. `system-operation` with persisted postcondition plus non-empty `postconditionEvidence` completes without project checks.
8. `system-operation` with only a trusted verifier can complete; verifier receives the profile fields.
9. Acceptance criteria still block all three explicit profiles before profile verification runs.

# Canonical Tool Registry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace manually synchronized tool-name, Goal eligibility, MCP annotation, capability, and App-owned broker method lists with one canonical registry while preserving the current 26-tool public contract and Host authorization authority.

**Architecture:** Add a dependency-light CommonJS registry under `shared/` so both Electron Desktop and the ESM Agent can consume the same static metadata. The Agent binds real `description`, `inputSchema`, `invoke`, and timeout values onto that metadata to form complete runtime descriptors; Desktop uses the same broker method metadata only to validate and route known methods, while existing Host handlers remain authoritative for authorization. Keep one independent literal contract test for the externally frozen tool catalog, but make normal registration, capabilities, Goal selection, broker validation, acceptance, and contract scripts derive from the registry.

**Tech Stack:** Node.js CommonJS + ESM, MCP server v2, existing Agent tool factories, Electron Desktop CommonJS host, Node test runner.

**Spec:** `docs/superpowers/specs/2026-08-29-v0.5-security-architecture-slim-ui-design.md` section 8.

## Global Constraints

- Preserve Desktop v0.4.11 and Agent Runtime v0.9.3 version numbers in this phase.
- Preserve the existing 26-tool no-broker public MCP surface and its order.
- Broker-enabled runtime keeps the existing 10 public `local_*` tools in the same insertion point before `goal_mode`.
- `host_approve_command` remains broker-internal and must never appear in model-facing MCP tool or capability lists.
- The broker server remains authoritative for Host-side authorization even when the Agent advertises a broker-backed tool.
- Existing shell, privilege-escalation, sensitive-path, sandbox, approval, process-isolation, Goal persistence, and broker-authentication boundaries must not be weakened.
- Do not implement Host decomposition, renderer work, package variants, version bumps, tags, releases, or installer changes in this phase.
- Keep `shared/**/*` packaging behavior unchanged; the existing package rule already includes the new registry module.

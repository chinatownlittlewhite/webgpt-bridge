# Crash-Recoverable Local File Transactions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the local file broker's exception-only rollback journal with a durable on-disk transaction protocol that can safely recover create/update/delete/move batches after a Desktop/OS crash without guessing whether a mutation completed.

**Architecture:** Introduce a focused `local-file-transaction-manager.cjs` module. Each approved batch is prepared in one `.webgpt-bridge-txn-<uuid>` directory placed beside the first touched path; before mutation, every participating parent directory must be verified to live on the same filesystem/device so every protected rename remains same-filesystem. A Host-private JSON registry under Electron `userData` durably points to active transaction directories, while `transaction.json` records paths, SHA-256 identities, operation order, and state (`prepared`, `applying`, `committed`, `rolling_back`) but never file contents. Broker initialization synchronously recovers registered transactions: prepared is cleaned, applying/rolling_back is restored to the exact pre-state, committed is verified as final then cleaned, and corrupt/ambiguous state fails closed.

**Tech Stack:** Node.js CommonJS, `node:fs`, `node:path`, `node:crypto`, Node test runner, existing Desktop broker/policy/audit infrastructure.

**Spec:** `docs/superpowers/specs/2026-08-29-v0.5-security-architecture-slim-ui-design.md` section 6, “Crash-recoverable local file batches”.

## Global Constraints

- Preserve existing model-facing `local_stage_changes` / `local_confirm_batch` schemas and response shapes.
- Preserve the existing SHA-256 precondition checks and confirmation policy; durable transactions start only after confirmation and revalidation.
- Never follow symlinks/reparse points for transaction directories, manifest files, backups, staged files, source files, or target files.
- Manifest/registry files may contain exact paths and hashes required for recovery but must not contain staged file contents or secret values from file contents.
- Use only standard Node filesystem primitives; do not add SQLite, native persistence modules, or new runtime dependencies.
- Cross-filesystem batches must fail before the first protected rename; do not degrade to copy/delete semantics.
- Recovery must prefer restoration over guessing success. Ambiguous or corrupt state remains on disk and startup fails closed with an actionable bounded error.
- Do not change Goal profiles, Tool Registry, Host decomposition, package pruning, UI, version numbers, installers, tags, or releases in this task.

- [ ] **Step 4: Implement prepare/apply/commit protocol**

For `commit({ batchId, changes })`:

1. Validate 1–20 normalized changes and a bounded batch id.
2. Choose `anchorParent = path.dirname(changes[0].type === "move" ? changes[0].from : changes[0].path)`.
3. Read `stat.dev` for the anchor parent and every source/target parent. If any differ, throw `LOCAL_TRANSACTION_CROSS_DEVICE` before creating `applying` state or mutating user files.
4. Create `<anchorParent>/.webgpt-bridge-txn-<uuid>` as a plain mode-0700 directory plus plain `new/` and `backup/` subdirectories.
5. For create/update, write staged bytes to `new/<index>`, fsync the staged file, and record only its SHA-256 in the manifest.
6. Durably publish `transaction.json` with state `prepared`.
7. Durably add `{ id, directory }` to the Host-private registry.
8. Durably replace the manifest state with `applying` **before** the first protected rename.
9. Apply in manifest order using only same-filesystem rename/remove operations:
   - create: `new/<index> -> path`
   - update: `path -> backup/<index>`, then `new/<index> -> path`
   - delete: `path -> backup/<index>`
   - move: `from -> backup/<index>`, then `backup/<index> -> path`
10. Fsync touched parent directories best-effort and verify the final state by exact hashes/existence.
11. Durably set state `committed`.
12. Durably unregister the transaction, then remove the transaction directory. If a process dies after unregister but before cleanup, the leftover directory is harmless because the committed final state was already verified.

`faultInjector({ phase, index, transactionId })` is a host-internal test seam only. The module itself converts a returned `"crash"` at deterministic phase boundaries into a private injected-crash exception and deliberately skips in-process rollback only for that private exception. Do not pass this option from `local-file-broker.cjs` or `main.cjs`.

- [ ] **Step 6: Implement deterministic recovery and rollback reconciliation**

`recoverPendingTransactions()` must iterate the validated registry in deterministic id order and validate each registered directory before touching anything:

- directory basename matches `.webgpt-bridge-txn-<id>` exactly;
- transaction directory, `new/`, and `backup/` are plain directories, not symlinks;
- `transaction.json` is a plain file, not a symlink;
- manifest version/id/state are valid;
- all recorded paths are absolute, bounded, contain no NUL, and their relevant parents remain on the transaction filesystem;
- every `new/<index>` / `backup/<index>` path is derived internally from the validated transaction directory, never trusted from arbitrary manifest paths.

State handling:

```text
prepared      -> no user-file mutation was permitted yet; unregister then cleanup
applying      -> durably set rolling_back; reconcile every operation in reverse order to pre-state
rolling_back  -> continue the same reverse reconciliation
committed     -> verify exact final state; unregister then cleanup
```

Rollback reconciliation must use existence + exact SHA identities instead of manifest progress flags:

- create: staged-new present + target absent is unapplied; target matching `newSha256` is removed; target with any other identity is ambiguous.
- update: backup matching `expectedSha256` restores over a missing/new-hash target; an untouched target matching `expectedSha256` with no backup is already pre-state; conflicting identities are ambiguous.
- delete: backup matching `expectedSha256` restores a missing target; untouched old-hash target with no backup is pre-state; conflicts are ambiguous.
- move: restore either `backup/<index>` or a target matching `expectedSha256` back to `from`; if `from` already matches expected and target/backup are absent, it is pre-state; all conflicting combinations are ambiguous.

On ambiguity, leave registry + transaction directory intact and throw an error with `code === "LOCAL_TRANSACTION_RECOVERY_REQUIRED"`. Never delete evidence after an ambiguous recovery.

- [ ] **Step 7: Add security RED tests**

# v0.5 Canonical Security Policy Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace duplicated Desktop/Agent authorization decision tables with one dependency-light shared policy core while preserving the intended v0.4.11/v0.5 Phase-One security decisions.

**Architecture:** Add `shared/security-policy-core.cjs` as the canonical pure decision engine. Existing Desktop and Agent modules remain compatibility adapters: they validate/normalize paths, argv, sandbox state, SSH target state, and command intent, then call the core; adapters may add stricter structural validation but may never promote a core `deny` to `confirm` or `allow`. The core returns `allow|confirm|deny`, stable rule id, reason, permission class, and remember scope; the Agent maps canonical `confirm` to its existing `approval_required` transport vocabulary.

**Tech Stack:** Electron 40, Node.js >=20, CommonJS shared/Desktop modules, ESM Agent modules, `node:test`; no new dependencies.

**Spec:** `docs/superpowers/specs/2026-08-29-v0.5-security-architecture-slim-ui-design.md`

## Global Constraints

- Preserve Desktop v0.4.11 / Agent Runtime v0.9.3 external compatibility; do not bump versions in this phase.
- Existing settings, runtime keys, workspace selection, handoff data, Goal state, MCP tools, broker protocol, and package identity remain unchanged.
- Existing shell, privilege-escalation, sensitive/system-path, sandbox-expansion, SSH, approval, and process-isolation boundaries must not be weakened.
- `full_control` remains a high-autonomy preset, never an immutable-boundary bypass.
- Phase-One Host capabilities, single-instance ownership, and authenticated broker sessions are inputs to this migration and must not be reopened or redesigned.
- `shared/**/*` is already included and unpacked by Desktop packaging; do not broaden package contents.
- Goal Store v2, crash-recoverable file transactions, Goal verification profiles, Tool Registry, `main.cjs` decomposition, package slimming, UI redesign, and release/tag work are out of scope.
- All production behavior changes use TDD: failing focused test first, minimal implementation, focused GREEN, then regression gate.

### Task 1: Add the canonical policy result schema and immutable decision engine

**Files:**
- Create: `shared/security-policy-core.cjs`
- Create: `test/security-policy-core.test.cjs`

**Interfaces:**
- Produces `authorizeSecurityOperation(operation)` where `operation.type` is one of `filesystem-path`, `filesystem-action`, `agent-command`, `agent-execution`, `terminal-command`, `host-command`, or `ssh`.
- Produces `normalizeApprovalPreset(value)` returning one of `cautious|development|auto|full_control`, defaulting to `development` for compatibility.
- Every result is frozen and has exactly:
  ```js
  {
    decision: "allow" | "confirm" | "deny",
    rule: string,
    reason: string,
    permissionClass: string | null,
    rememberScope: "none" | "connection" | "single-use",
  }
  ```
- The core never accepts caller-provided `decision`, `rule`, `permissionClass`, or `rememberScope` as authority.

- [ ] **Step 1: Write failing core contract tests**

Cover:
- invalid/missing operation type fails closed;
- returned object is frozen and contains the normalized five-field schema;
- `filesystem-path`: system/sensitive direct access deny; workspace allow; known-folder/ordinary Host read/list confirm; non-read ordinary Host operations preserve current allow behavior;
- `filesystem-action`: sensitive read/list confirm with `single-use`; sensitive mutation/execute deny; cautious workspace destructive confirm; development/auto workspace destructive allow; outside-workspace destructive confirm; `full_control` ordinary network/Host behavior can allow but sensitive remains protected;
- `agent-command`: immutable shells/privilege escalation/remote file transfer deny; known project checks and safe Git reads allow; Git mutation/package mutation/runtime/unknown command classes confirm;
- `agent-execution`: a base allow is downgraded to confirm when the sandbox is not verified/auto-run-safe, while base deny stays deny;
- `host-command`: base deny is immutable; sandbox expansion and unverified sandbox confirm before preset auto-approval; existing cautious/development/auto/full_control decisions remain equivalent;
- `ssh`: unsafe option/target/missing remote command deny; a validated allowed target remains approval-gated rather than auto-allowed.

- [ ] **Step 2: Run RED**

Run:
```text

```
Expected: FAIL because `shared/security-policy-core.cjs` does not exist.

- [ ] **Step 3: Implement the minimal pure core**

Use small internal helpers only. Keep command/path parsing out of the core; consume normalized classes/booleans. Preserve existing rule identifiers where they already represent stable behavior (`always-deny`, `ssh-network`, `git-read-only`, `git-path-sensitive`, `git-mutation`, `project-check`, `package-manager`, `runtime-execution`, `sensitive-command`, `default-ask`) and add stable filesystem/sandbox ids only where no shared id exists.

Host-command input must be normalized to booleans such as:
```js
{
  type: "host-command",
  preset,
  baseDecision: "allow" | "confirm" | "deny",
  baseRule,
  commandName,
  sandboxVerified,
  sandboxExpanded,
  projectScript,
  safeDependencySync,
  gitTrustedSync,
  gitReadOnlyRemote,
  developmentGitMutation,
  gitPush,
  gitRiskyRemote,
  githubRead,
  githubExternalWrite,
  safeWorkspaceUtility,
  highAutonomyUtility,
}
```
The result permission class should be populated only when the existing behavior is connection-rememberable; sensitive access uses `single-use` and null permission class.
